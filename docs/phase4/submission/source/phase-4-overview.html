3. Quality and testing

  • CI on every pull request: type checks and 598 unit, API and database tests against a real MongoDB with none skipped; 17 browser journeys against the live API with MongoDB and Mailpit; 22 mock-mode browser checks, including no sideways scrolling on 14 pages at 320–1440 px and at browser font sizes of 18, 20 and 24 px; a production image build.
  • Deployed site: Lighthouse accessibility 100 and SEO 100 on the six pages measured, mobile performance 94–100; a footer layout shift of up to 0.7 found and fixed (0–0.001 on five pages).
  • Security: bcrypt passwords; one-hour signed tokens with the role re-read from the database; rate limits on sign-in, registration, enquiries, orders and quotes; CORS allowlist and security headers; strict input validation and body limits; logs without passwords, tokens, bodies or database messages; the proxy setting measured on the host; npm audit reduced from 31 findings to 2 unreachable moderate ones; a secrets scan of every commit.

5. Known limitations

  • Checkout is simulated by design; the WhatsApp link stays hidden until the business gives a real number.
  • The rollback procedure is written but not yet rehearsed on Railway; the live journeys that sign in or read the deployed inbox are run by people, not in CI.
  • At browser fonts of 28 px and more on a 320 px screen, some long words still scroll sideways; 18–24 px (Chrome's larger settings) fit on every page.
  • HTTP builds still ship the mock adapters (never used in HTTP mode); Lighthouse best practices is 96 because the security policy blocks a library's one-time check.
