AI Usage Report

Phase 2 (front-end development) · Prepared 28 October 2026 · Aman Gulati, Varad Tambe, Reethika Gajulapati, Krish Ruparel, Daniel Yglesias

1. Summary

We used AI coding assistants throughout the project as pair programmers. Four members used Claude Code (Anthropic) and one used Codex (OpenAI). The team set the requirements, architecture, task definitions, design decisions and acceptance criteria. Each member directed an assistant within their own area. The assistants drafted most of the implementation code and tests from those specifications. Every change was reviewed, run and tested by a team member and approved by a second member before it was merged. We are responsible for all submitted work.

3. How we used AI

Planning and requirements

We used the assistants to turn the course checkpoints and the project blueprint into per-member phase plans, shared data contracts and an ownership map. The team then reviewed these and changed them where needed, for example the data model (ERD), the mock-first plan for Phase 2 and the merge order.

Implementation

Each member gave their assistant a scoped task for their own area and phase, limited to the files they own. The assistant drafted the code and tests. The member reviewed the diff, ran the app at phone and desktop widths in English and Spanish, and asked for revisions before committing.

Code review

Reviewers used assistants to run the full checks and summarize a pull request against the contracts and ownership rules. The decision to approve or request changes was always made by the reviewer. Krish's review of the shell foundation (#3), for example, raised seven points:

  • a missing desktop sign-out;
  • an accessibility mismatch between visible and spoken link labels (WCAG 2.5.3);
  • contract changes that needed the affected owners' review;
  • a schema section deleted by mistake;
  • inaccurate test counts in the evidence.

All seven were fixed before he approved. He also requested changes on the image library (#8).

Integration, CI and debugging

The coordinator used Claude Code to wire cross-area dependencies (authentication middleware, quote notifications) and to find the root cause of CI failures:

  • the database image could not start on GitHub's newer runners;
  • two timing-dependent tests;
  • tests that still expected placeholder pages.

Each fix went through a reviewed pull request.

Quality assurance and documentation

Assistants helped run the submission checklist, the WCAG 2.2 AA audit and the contrast and reflow measurements, publish the static demo to GitHub Pages and run Google PageSpeed Insights on the live pages. They also drafted evidence files and weekly records from actual test output, and the team checked them.

5. What the team did

  • Direction and design. We chose the project, split it into five owned areas, picked the stack, and decided the data model, authentication approach, mock-first Phase 2 plan and bilingual requirement. We also set the visual direction and the policy of fictional data and CC0 imagery only.
  • Task definition. Each member decided what their assistant should build, broke it into steps and set the acceptance criteria from the course and blueprint requirements.
  • Review and testing. Every merged pull request was approved by a member other than its author: 21 approvals and 2 change requests across 21 merged PRs. Feature PRs were visually reviewed at phone and desktop widths in English and Spanish. Daniel and Krish re-ran the full test suite themselves before approving the integration (#12) and the first release (#16).
  • Product decisions from hands-on testing. Daniel identified that the sampler should reset after an enquiry and that shoppers needed a quantity picker (#14, #15). Krish's review added the desktop sign-out and fixed the language-switch labels (#3).
  • Integration and process decisions. The coordinator decided merge order, ownership exceptions and the release process, and configured branch protection. When an assistant suggested changing the repository's default branch, we checked the suggestion against the course's GitHub guidelines first and rejected it. When the uta.cloud account turned out to have no hosting space, the coordinator confirmed with the professor that a third-party host was acceptable before the demo was published on GitHub Pages.

6. Safeguards and verification

  • Protected branches: nothing merges without passing CI and approval from a second person, admins included.
  • Automated checks on every pull request: type checking, 531 unit and integration tests (including each member's real-MongoDB persistence suite), structure checks and a production build. The Playwright browser journeys were run before each merge.
  • No secrets, credentials or personal data were shared with AI tools; all demo data is fictional.
  • Assistants were limited to the requesting member's own files; anything shared went through a proposal and a reviewed pull request.
  • AI output was not accepted as is. Problems we caught and corrected include tests coupled to placeholder pages, two timing-dependent tests, a CI environment incompatibility and the reflow failure found in the accessibility audit.

7. Reflection

The assistants let a five-person team build a large, well-tested application in a short time. What made that work was the structure we put around them: clear ownership, shared contracts, required peer review and automated tests. The biggest risks we saw were confident but wrong suggestions and tests that passed for the wrong reasons. Human review and real-database testing caught both. In Phase 3 we will keep the same process while connecting the interface to the live API.
